# 交易日历与确认日查询工具规格

## 1. 输入格式

### 1.1 单笔计算

请求：`POST /api/query`

```json
{
  "submit_time": "2025-01-22 15:00",
  "fund_type": "EQ"
}
```

- `submit_time` 必填，格式必须为 `YYYY-MM-DD HH:MM`，使用 24 小时制，精确到分钟，不接受秒、时区、`T` 分隔符或其他格式。
- 日期必须落在日历覆盖范围 `2024-01-01` 至 `2026-12-31` 内。
- `fund_type` 必填，只允许 `EQ`、`BD`、`QDII`。

### 1.2 批量计算

请求：`POST /api/batch`

```json
{
  "items": [
    {"apply_id": "APP0001", "submit_time": "2025-01-22 15:00", "fund_type": "EQ"}
  ]
}
```

- `items` 必须是非空数组，单次最多 100000 条。
- 每条记录遵守单笔计算的输入规则；`apply_id` 为可选透传字段。
- 批量请求结构错误（缺少 `items`、空数组、超过上限）返回整体错误。
- 单条记录非法时，其他记录仍可计算；该条在结果数组对应位置返回错误信息，并保留可识别的原始字段或 `apply_id`。

## 2. 日期算法

所有日期判断以 `data/ashare_calendar_2024_2026.csv` 和 `data/us_calendar_2024_2026.csv` 为准，不使用周一至周五的简单推算。

### 2.1 境内基金的 T 日候选

1. 提交日是境内交易日，且提交时间小于或等于 `15:00`：T 日候选为提交日。
2. 提交日是境内交易日，且提交时间晚于 `15:00`（例如 `15:01`）：T 日候选为下一个境内交易日。
3. 提交日不是境内交易日，无论提交时间为何：T 日候选为该日之后（含顺延起点搜索）的第一个境内交易日。
4. 非交易日和超过截止时间不能重复顺延。例如，周六上午提交与同一周周五 `15:30` 提交，通常得到同一个下周一 T 日。

### 2.2 EQ 和 BD

- EQ 和 BD 使用境内交易日历。
- 确认日是 T 日之后第 1 个境内交易日，即 T+1；计数不包含 T 日。

### 2.3 QDII

- QDII 的 T 日必须同时是境内和美股共同交易日。
- 先按 2.1 计算境内 T 日候选；如果该候选日美股休市，则顺延到候选日之后第一个共同交易日。
- QDII 确认日先取 T 日之后第 2 个境内交易日，即 T+2；计数不包含 T 日。
- 如果上述 T+2 候选日美股休市，则顺延到该日之后第一个共同交易日。
- QDII 的共同交易日约束同时适用于 T 日和确认日，不能只使用境内交易日历。

### 2.4 查询日

- 查询日是确认日之后的第一个境内交易日，严格晚于确认日。
- 查询日只按境内交易日历判断，不要求美股同日开市。

## 3. 日历文件校验

服务启动时必须同时校验境内和美股两份日历。任一文件校验失败，服务不得启动或不得进入可查询状态，并应返回明确的启动错误。

每份日历必须满足：

- 文件存在且可读取；
- 使用 UTF-8（可带 UTF-8 BOM）编码；
- CSV 表头为 `date,is_trading_day`，字段完整且无额外字段；
- `date` 是合法的 ISO 日期 `YYYY-MM-DD`；
- `is_trading_day` 只能是 `0` 或 `1`；
- 日期不能重复；
- 按日期排序后必须每天连续，不能有日期断档；
- 日期范围必须完整覆盖 `2024-01-01` 至 `2026-12-31`，不能缺少起始日、结束日或中间日期；
- 文件不能为空。

文件缺失、编码错误、CSV/表头格式错误、空文件、日期格式错误、交易标记错误、重复日期、日期断档或范围不完整，均属于日历配置错误，不能降级使用或静默修复。

## 4. API 返回约定

### 4.1 统一响应

成功：

```json
{
  "success": true,
  "data": {},
  "error": null
}
```

输入或业务错误：HTTP 400：

```json
{
  "success": false,
  "data": null,
  "error": {
    "code": "INVALID_INPUT",
    "message": "具体错误原因"
  }
}
```

未知接口返回 HTTP 404 和 `NOT_FOUND`。服务内部异常返回 HTTP 500 和统一 JSON 错误，不返回 HTML 错误页。

### 4.2 单笔查询

`POST /api/query` 成功时，`data` 至少包含：

```json
{
  "submit_time": "2025-01-22 15:00",
  "fund_type": "EQ",
  "T_date": "2025-01-22",
  "confirm_date": "2025-01-23",
  "query_date": "2025-01-24",
  "reasons": ["...每一步的判断依据..."]
}
```

`reasons` 必须能够解释提交日归属、15:00 截止时间、基金类型对应的 T+N、QDII 共同交易日顺延（如适用）以及查询日的取得方式。

### 4.3 批量查询

`POST /api/batch` 成功时，`data` 至少包含：

```json
{
  "items": [],
  "count": 1
}
```

结果顺序必须与输入顺序一致，并保留输入中的 `apply_id`。批量结果应支持后续导出为 CSV，导出字段至少包括 `apply_id`、`T_date`、`confirm_date`、`query_date`；单条错误也必须在对应位置可追溯。

### 4.4 日历查询

请求：`GET /api/calendar?date=2025-01-22&market=A_SHARE`

- `date` 必须是合法日期且在覆盖范围内。
- `market` 只能是 `A_SHARE` 或 `US`。
- 成功数据至少包含 `date`、`market`、`is_trading_day`、`next_trading_day`。
- `next_trading_day` 是严格意义上的下一个交易日；当查询日不是交易日时，应返回该日之后第一个交易日。

### 4.5 历史查询

请求：`GET /api/history`，可选 `limit` 参数。

- 历史记录必须持久化到 SQLite；至少保留请求时间、请求类型、原始请求、成功结果或错误结果。
- `limit` 必须是 1 至 500 的整数；默认返回最近记录。
- 返回结果应按记录时间倒序，能够追溯单笔和批量请求。

### 4.6 健康检查

`GET /api/health` 成功时返回服务可用状态，例如：

```json
{"success": true, "data": {"status": "ok"}, "error": null}
```

## 5. 必须测试的案例

以下案例至少必须覆盖；日期结果以当前提供的两份日历为准。

| 1 | `2025-01-22 14:59`, EQ | T=`2025-01-22`，确认=`2025-01-23`，查询=`2025-01-24` |
| 2 | `2025-01-22 15:00`, EQ | 与 14:59 相同，验证 15:00 包含边界 |
| 3 | `2025-01-22 15:01`, EQ | T=`2025-01-23`，验证超过截止时间顺延 |
| 4 | `2025-01-24 15:30`, EQ | T=`2025-01-27`，验证周五晚提交 |
| 5 | `2025-01-25 09:30`, EQ | T=`2025-01-27`，应与案例 4 相同 |
| 6 | `2025-01-26 15:00`, BD | 周日提交，T=`2025-01-27` |
| 7 | `2025-01-29 10:00`, EQ | 春节长假后顺延至 `2025-02-05` |
| 8 | `2025-10-01 00:00`, EQ | 国庆长假后顺延至 `2025-10-09` |
| 9 | `2025-04-03 15:00`, QDII | 验证境内节日前后及 QDII T+2 |
| 10 | `2025-01-20 10:00`, QDII | 境内开市但美股休市，T 应顺延至 `2025-01-21` |

| 12 | `2025-06-19 16:00`, QDII | 境内/美股休市差异与超过 15:00 同时出现 |

| 14 | `2025-12-31 15:01`, QDII | T、确认日、查询日均跨年，验证范围内跨年计算 |

| 20 | 缺少 `submit_time` 或 `fund_type` | 必填字段缺失，返回 HTTP 400/`INVALID_INPUT` |
| 21 | 批量 `items=[]` | 空批量请求返回整体错误 |
| 22 | 日历查询 `market=XXX` | 非法市场参数返回 HTTP 400/`INVALID_INPUT` |
| 23 | 日历查询超出 2024-01-01 至 2026-12-31 | 日期范围错误，返回 HTTP 400/`INVALID_INPUT` |
| 24 | 删除、截断或制造重复日期的日历文件后启动 | 服务拒绝启动并报告日历配置错误 |
